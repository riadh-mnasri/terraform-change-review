# Google provider plan validation

The regression suite reads complete JSON plans generated by Terraform 1.15.7 and `hashicorp/google` 7.13.0. The provider is real; all identities, configuration and prior state are synthetic. No GCP resources were created or read to produce these fixtures.

## What is covered

Six resource types are exercised: `google_project_iam_member`, `google_project_iam_binding`, `google_storage_bucket_iam_member`, `google_storage_bucket_iam_binding`, `google_compute_firewall` and `google_storage_bucket`.

| Fixture | Configuration change | Expected review |
|---|---|---|
| `create.json` | Create the baseline, including editor/owner assignments | Two `GCP-IAM-ELEVATED` findings; computed values remain unknown |
| `risky-update.json` | Remove a project IAM condition; add public IAM principals; open explicit IPv4/IPv6 firewall sources; enable `force_destroy`; disable uniform bucket access | Ten findings: nine HIGH, one MEDIUM, including two `TF-REPLACE` findings |
| `condition-expression.json` | Change a retained assignment's condition expression to `true` | `GCP-IAM-CONDITION-CHANGED` (MEDIUM) and `TF-REPLACE` (HIGH); no CEL implication inference |
| `labels-only.json` | Change a bucket label | No findings, including for computed-only firewall differences introduced by the synthetic state |
| `recovery.json` | Restore baseline restrictions from the risky configuration | Two `TF-REPLACE` findings; no specialized risk findings |

The `risky-update` findings cover `GCP-IAM-ELEVATED`, `GCP-IAM-PUBLIC`, `GCP-IAM-CONDITION-REMOVED`, `GCP-FIREWALL-WORLD`, `GCP-BUCKET-DESTROY`, `GCP-BUCKET-ACCESS` and generic replacement reporting. Tests assert rule/resource pairs and selected evidence, rather than snapshots containing timestamps.

The baseline is not a recommended security configuration: it deliberately includes curated sensitive roles so the creation path is tested. Fixture names describe changes, not safety verdicts.

## Reproduce the exports

Requirements: Terraform **1.15.7**, Python **3.9+**, and network access to download the pinned Google provider. Java is needed only to run the analyzer tests. No Google account, credentials, Terraform backend or infrastructure repository is required.

From the repository root:

```sh
terraform version
terraform fmt -check src/test/resources/google-generated/main.tf
python3 scripts/generate-google-fixtures.py
./mvnw --batch-mode --no-transfer-progress clean verify
java -jar target/terraform-change-review.jar review src/test/resources/google-generated/risky-update.json --format markdown --fail-on none
```

The generator:

1. Copies the fixture HCL and committed provider lockfile into a temporary directory.
2. Checks the exact Terraform version, initializes the provider with `-backend=false -lockfile=readonly`, and validates the HCL.
3. Plans the baseline from an empty state with `-refresh=false` and exports it using `terraform show -json`.
4. Converts the baseline's known planned values into a **fabricated local state**, retaining provider schema versions and assigning synthetic IDs. Unknown/computed values are not populated with cloud results.
5. Plans the risky, expression and label scenarios against that state. It also fabricates state from the risky plan to generate the recovery scenario.
6. Writes the five JSON exports only after all plans succeed, then removes the temporary workspace. The exported JSON values are not patched or hand-edited.

There is no `apply`, `destroy`, `import`, refresh or data source in this workflow. A fixed nonfunctional access token is supplied in the fixture HCL. The subprocess uses a temporary home directory and removes ambient Google credentials and Terraform variable/CLI argument overrides from its environment. It preserves `TF_CLI_CONFIG_FILE` and `TF_PLUGIN_CACHE_DIR` for an existing provider mirror or cache; any configured mirror must supply the exact package accepted by the committed lockfile. Downloading the provider requires network access unless already mirrored or cached.

The checked-in lockfile covers macOS and Linux on AMD64 and ARM64. If a platform or provider version changes, regenerate and review the lockfile with `terraform providers lock`; do not bypass checksum validation. The provider is pinned for reproducible fixtures, not as a recommendation for production.

## How to review regenerated files

Check the HCL and generator diff before reviewing JSON. Confirm the Terraform/provider versions and resource actions, then run `GoogleProviderPlanTest` through Maven. Review findings and evidence in the CLI output. Timestamps and some metadata can change between runs; compare observable behavior rather than requiring byte-identical exports.

All changes, including regenerated fixtures and documentation, go through a dedicated branch and pull request. Never replace these files with a real plan or add a state file, provider binary, saved binary plan or credentials.

## Limits of this validation

The tests exercise one Terraform/provider combination and selected transitions. They do not validate Google API acceptance, resource existence, refresh behavior, successful apply, effective IAM, organization policies or network reachability. For example, an organization policy may prohibit a public principal that still appears in a local plan.

Because the prior state is fabricated from planned values, it lacks some computed attributes a real apply would return. The provider can therefore plan computed-only changes, such as an unknown firewall `destination_ranges`, even in the label scenario. Tests explicitly check that these do not become unrelated risk findings. These exports must not be described as plans captured from deployed GCP infrastructure.

GKE and Cloud SQL checks, unknown rule-input handling, sensitivity-mask redaction and additional edge cases remain covered by the hand-written regression suite. This is neither a provider compatibility matrix nor a complete Claude Code conversation test.
